## 1. Агенты для email-рассылок

Минимальный состав — 6 агентов. Каждый агент имеет узкую зону ответственности, свой вход/выход и не трогает чужие данные.

| # | Агент | Задача | Вход | Выход |
|---|-------|--------|------|-------|
| 1 | **Segment Agent** (сегментатор) | Делит базу на сегменты, поддерживает актуальность тегов | База из CRM (обезличенные ID + атрибуты) | Списки ID по сегментам |
| 2 | **Copy Agent** (копирайтер) | Пишет тексты писем и цепочек под сегмент и цель кампании | Бриф кампании, портрет сегмента, тон бренда KAVCOSMO | Черновики писем с плейсхолдерами |
| 3 | **QA Agent** (контролёр) | Проверяет письма перед отправкой: факты, ссылки, спам-триггеры, персонализация, юридические требования | Черновик письма | Отчёт проверки + правки / «допущено к отправке» |
| 4 | **Reply Agent** (обработчик ответов) | Классифицирует входящие ответы, готовит черновики ответов, ставит задачи менеджеру | Входящие письма из Gmail | Классификация (интерес / вопрос / отказ / отписка / автоответ) + черновик ответа |
| 5 | **Hygiene Agent** (гигиена базы) | Обрабатывает отписки, жалобы, bounce'ы; чистит и дедуплицирует базу | Webhooks/отчёты сервиса рассылок | Обновлённые статусы контактов, стоп-лист |
| 6 | **Analytics Agent** (аналитик) | Собирает метрики кампаний (open/click/reply/bounce/unsub), делает выводы, предлагает A/B-тесты | Статистика сервиса рассылок | Отчёт по кампании + рекомендации |

Опционально на следующих этапах:

- **Orchestrator Agent** — управляет пайплайном «сегмент → письмо → проверка → отправка → аналитика», следит за расписанием и лимитами отправки.
- **Enrichment Agent** — обогащает карточки (город, специализация, источник) из открытых данных, которые контакт сам указал при подписке.

Принцип: **ни один агент не имеет права отправлять письма напрямую**. Отправка — только через сервис рассылок после подтверждения человеком (на первых этапах) или после прохождения QA-чеклиста (позже).

## 2. Необходимые скиллы

Скиллы — переиспользуемые «умения», которые подключаются агентам:

1. **`email-copywriting`** — тон KAVCOSMO, структура письма (тема → прехедер → лид → оффер → CTA → подпись), ограничения по длине, запрещённые формулировки.
2. **`segment-briefing`** — как описывать сегмент: боли, стадия воронки, что уже получал, что предложить.
3. **`spam-check`** — чеклист спам-триггеров: стоп-слова, соотношение текст/ссылки, капс, вложения, вес письма.
4. **`personalization`** — правила подстановки плейсхолдеров, fallback-значения («коллега», «ваш город»), проверка, что ни один `{{...}}` не ушёл незаполненным.
5. **`reply-classification`** — таксономия ответов и правила маршрутизации (кому эскалировать, что отвечать автоматически).
6. **`list-hygiene`** — правила обработки hard/soft bounce, отписок, жалоб, неактивных контактов.
7. **`campaign-analytics`** — какие метрики считать нормой, как читать статистику, когда останавливать кампанию.
8. **`compliance`** — требования законодательства о рекламе и персональных данных: согласие на рассылку, обязательная ссылка отписки, идентификация отправителя, хранение доказательств согласия.

## 3. Где хранить базу косметологов

**Главный принцип: база живёт вне GitHub.** GitHub — только код, шаблоны и отчёты без персональных данных.

Рекомендуемая схема (по слоям):

| Слой | Инструмент | Что хранится |
|------|-----------|--------------|
| **Мастер-база (source of truth)** | CRM — **HubSpot** (уже подключён к рабочему пространству через MCP) либо аналог | Полные карточки: контакты, история касаний, статусы, согласия |
| **Операционный слой рассылок** | Сервис рассылок (см. раздел 14) | Синхронизированные списки/сегменты, статусы доставляемости |
| **Рабочий слой для Claude** | Google Sheets / выгрузки по запросу | Только необходимый срез, желательно обезличенный (ID + сегмент + атрибуты без ФИО/email) |
| **GitHub** | этот репозиторий | Схема полей, правила сегментации, шаблоны писем с плейсхолдерами, отчёты — **без единого реального контакта** |

Почему CRM, а не таблица:

- согласия и история взаимодействий фиксируются автоматически;
- отписки и bounce синхронизируются с сервисом рассылок без ручной работы;
- права доступа управляются централизованно;
- при росте базы (>1–2 тыс. контактов) таблицы перестают быть управляемыми.

Google Sheets допустим как временный этап на старте (до ~500 контактов), но с самого начала структура таблицы должна повторять схему CRM (раздел 4), чтобы миграция была переносом, а не переделкой.

## 4. Структура таблицы

Три сущности (в CRM это объекты, в Sheets — три листа):

```
CONTACTS (косметологи)
   │ 1 ко многим
   ├──► TOUCHES (касания: отправки, открытия, ответы)
   │
CAMPAIGNS (кампании)
   │ 1 ко многим
   └──► TOUCHES
```

- **CONTACTS** — одна строка = один косметолог. Уникальный ключ — `contact_id` (не email: email может смениться).
- **CAMPAIGNS** — одна строка = одна кампания/цепочка: цель, сегмент, даты, статус, метрики.
- **TOUCHES** — журнал событий: `contact_id + campaign_id + тип события + дата`. Отсюда считается вся аналитика и правило «не чаще N писем в месяц на контакт».

### CAMPAIGNS

`campaign_id`, `name`, `goal` (продажа / прогрев / реактивация / анонс), `segment`, `sequence_length` (число писем в цепочке), `start_date`, `end_date`, `status`, `sent` / `delivered` / `opens` / `clicks` / `replies` / `unsubs` / `bounces`, `revenue_attributed`, `owner`.

### TOUCHES

`touch_id`, `contact_id`, `campaign_id`, `type` (sent / delivered / open / click / reply / unsub / bounce / complaint / manual), `timestamp`, `details`.

## 6. Сегментация косметологов

Сегментируем по **четырём осям**, сегмент = пересечение осей:

**Ось 1 — отношения с KAVCOSMO (важнейшая):**

| Сегмент | Критерий |
|---------|----------|
| 🆕 Новые лиды | Есть согласие, покупок нет, в базе < 30 дней |
| 🌱 Подписчики без покупок | Согласие есть, покупок нет, > 30 дней |
| 🛒 Первая покупка | 1 заказ за последние 90 дней |
| 🔁 Повторные клиенты | 2+ заказа |
| 👑 VIP | Верхние ~10% по сумме покупок или оптовики |
| 😴 Спящие | Была активность/покупки, но > 120 дней тишины |
| ⛔ Стоп-лист | Отписка, жалоба, hard bounce, отозванное согласие — **не трогаем никогда** |

**Ось 2 — профессиональный профиль:** специализация (эстетист / врач / массажист / брови-ресницы / владелец салона) — определяет, какие продукты и темы релевантны.

**Ось 3 — активность в письмах:** активные (открывали за 90 дней) / полуактивные / неактивные — определяет частоту и агрессивность рассылки.

**Ось 4 — гео:** город/регион — для локальных событий, сроков доставки, региональных офферов.

Правила:

- один контакт — в одной кампании одновременно; приоритет: транзакционные > ответные > кампании;
- сегмент «Стоп-лист» исключается из любых выборок на уровне сервиса рассылок (suppression list), а не вручную;
- сегменты пересчитываются автоматически перед каждой кампанией, а не «замораживаются» списком.

## 7. Первые кампании

Порядок — от наименее рискованных к более массовым:

1. **Welcome-цепочка для новых лидов** (3 письма: знакомство с KAVCOSMO → польза/экспертный контент → первый оффер). Лучший сегмент: тёплые, ждут писем, высокий open rate — идеально для прогрева домена.
2. **Прогрев подписчиков без покупок** (2–3 письма: экспертный контент для косметологов + мягкий оффер на первый заказ). Проверяем, что база живая, собираем статистику.
3. **Реактивация спящих клиентов** (1–2 письма: «мы скучаем» + персональный повод вернуться). Небольшими партиями — сегмент рискованный по bounce/жалобам.
4. **Анонсы новинок/акций для активных клиентов** — регулярный формат после того, как первые три показали здоровые метрики.
5. **VIP/оптовики** — персональные письма, полуручной режим, максимум персонализации.

Чего **не** делать в первых кампаниях: массовый «холодный» блас по всей базе разом, покупные списки, письма контактам без подтверждённого согласия.

## 8. Подготовка писем

Пайплайн:

```
Бриф кампании → Copy Agent: черновик → QA Agent: проверка → правки
→ человек: финальное утверждение → вёрстка/загрузка в сервис
→ тест на себя → отправка сегменту
```

Требования к письму:

- **Бриф обязателен**: сегмент, цель, одно ключевое действие (один CTA), оффер, дедлайн.
- **Структура**: тема (до ~50 знаков) → прехедер (дополняет тему, не дублирует) → приветствие с персонализацией → 1 мысль → 1 CTA → подпись живого человека → футер (реквизиты + отписка).
- **Персонализация** через плейсхолдеры (`{{first_name}}`, `{{city}}`) c обязательными fallback-значениями.
- **Тон KAVCOSMO**: письмо коллеге-профессионалу, а не «рекламный листок»; экспертность, без агрессивных продаж.
- На каждую кампанию — **2 варианта темы** для A/B-теста.
- Шаблоны хранятся в этом репозитории (`templates/`), только с плейсхолдерами; финальные письма с подстановкой живут в сервисе рассылок.

## 9. Проверка писем перед отправкой

Чеклист QA Agent (письмо не уходит, пока все пункты не «зелёные»):

**Контент:**
- [ ] Факты верны: цены, названия продуктов, даты, условия акции.
- [ ] Все ссылки кликабельны и ведут куда заявлено (UTM-метки проставлены).
- [ ] Ни одного незаполненного `{{плейсхолдера}}`; fallback-значения работают.
- [ ] Один CTA, оффер понятен с первого экрана.
- [ ] Орфография/пунктуация, тон соответствует бренду.

**Доставляемость:**
- [ ] Нет спам-триггеров: капс в теме, «!!!», «бесплатно» в лоб, укорачиватели ссылок, тяжёлые вложения.
- [ ] Соотношение текст/картинки разумное (письмо читабельно с отключёнными картинками).
- [ ] Вес письма < 100 КБ (иначе Gmail обрезает).
- [ ] Ссылка отписки на месте и работает.

**Комплаенс:**
- [ ] Сегмент содержит только контакты с `consent_status = есть согласие`.
- [ ] Идентификация отправителя (имя, реквизиты) в футере.

**Тест:**
- [ ] Тестовое письмо отправлено на внутренние ящики (Gmail, Яндекс, Mail.ru), проверено на десктопе и телефоне.
- [ ] Тест не упал в «Спам»/«Промоакции» неожиданным образом (для B2B-писем «Промоакции» приемлемо, «Спам» — стоп).

На первых 5–10 кампаниях финальное «отправить» нажимает **человек**, не агент.

## 10. Обработка ответов из Gmail

Ответы — самый ценный сигнал (и для продаж, и для доставляемости), поэтому обрабатываются в приоритете:

1. **Сбор**: рассылка идёт с реального ящика (или с reply-to на реальный ящик). Reply Agent читает входящие через Gmail-интеграцию (Gmail MCP-коннектор / API).
2. **Классификация** каждого ответа:
   - 🔥 **Интерес/заказ** → черновик ответа + задача менеджеру «связаться сегодня»;
   - ❓ **Вопрос** (о продукте, доставке, сертификатах) → черновик ответа на утверждение человеку;
   - 🙅 **Отказ/негатив** → пометка в CRM, пауза кампаний для контакта; при явном «не пишите» — обработка как отписки;
   - ✉️ **«Отпишите меня» текстом** → немедленно в стоп-лист (см. раздел 11), подтверждающий ответ;
   - 🤖 **Автоответ** (отпуск, смена адреса) → парсинг нового адреса не делаем автоматически; пометка, перенос следующего касания;
   - 📭 **Bounce-уведомления** → Hygiene Agent, обновление `email_validity`.
3. **SLA**: горячие ответы — реакция в тот же рабочий день; остальное — 24 часа.
4. **Фиксация**: каждый ответ пишется в TOUCHES; ответившим ставится на паузу текущая цепочка (человек ответил — автоматика молчит).
5. Claude **не отправляет ответы сам** на первых этапах — только готовит черновики; человек утверждает и отправляет.

## 11. Обработка отписок

Правило: **отписка исполняется мгновенно и необратимо** (вернуть контакт может только новое явное согласие от него самого).

Каналы отписки и обработка:

| Канал | Обработка |
|-------|-----------|
| Клик по ссылке отписки | Сервис рассылок автоматически ставит статус «отписан» и исключает из отправок |
| «Отпишите меня» в ответе | Reply Agent помечает → человек/скрипт ставит статус в CRM и в сервисе в тот же день |
| Жалоба на спам (FBL) | Немедленно в стоп-лист + разбор: из какого сегмента/письма пришла жалоба |
| Устная просьба менеджеру | Менеджер ставит статус вручную, стандартная процедура |

Технические требования:

- отписка **в один клик**, без логина и «опросов перед выходом» (опциональная страница предпочтений — можно, но кнопка «отписаться от всего» обязательна и первая);
- заголовки `List-Unsubscribe` + `List-Unsubscribe-Post` (one-click) — обязательны, Gmail требует их для массовых отправителей;
- единый **suppression list** на уровне сервиса рассылок: даже если сегмент собран с ошибкой, отписанному письмо не уйдёт;
- синхронизация статусов сервис ↔ CRM — автоматическая (webhook/нативная интеграция), не ручная;
- норма отписок < 0,5% на кампанию; больше — стоп и разбор.

## 12. Как не попасть в спам

**Техническая база (до первого письма):**

1. **SPF, DKIM, DMARC** настроены на домене отправки. DMARC начинаем с `p=none` (мониторинг), затем ужесточаем.
2. **Отдельный поддомен для рассылок** (например, `mail.kavcosmo.ru`) — репутация основного домена не страдает.
3. **Прогрев домена/ящика**: первые 2–4 недели — малые объёмы (десятки писем в день) по самым активным сегментам, объём наращиваем постепенно (~×1,5–2 в неделю).
4. **Верификация базы** до первой отправки (сервисы проверки email): hard bounce > 2% — удар по репутации.
5. Регистрация в **Google Postmaster Tools** — мониторинг репутации домена в Gmail.

**Практика отправки:**

- только контакты с согласием; никаких покупных баз;
- ровный график отправок (не «тишина месяц → бласт на всю базу»);
- частота: не чаще 1 письма в неделю на контакт (для B2B-базы косметологов оптимум — 2–4 письма в месяц);
- неактивных > 6 месяцев — не грузить массовыми письмами: сначала маленькая реактивационная кампания, не открыл — в архив;
- текстовая часть всегда присутствует (не «письмо-одна-картинка»); ссылки — на свой домен, без укорачивателей;
- следить за метриками: жалобы < 0,1% (порог Gmail — 0,3%, ближе подходить нельзя), bounce < 2%, open rate по активным сегментам > 20%.

**Красные линии:** резкий рост объёма, рассылка по неактивным без реактивации, отсутствие отписки, скрытие отправителя — любой из пунктов может убить домен на месяцы.

## 13. Что можно делать через Claude

Claude силён там, где нужны язык, анализ и рассуждение:

- ✅ написание и вариации писем/цепочек под сегменты, A/B-варианты тем;
- ✅ QA-проверка писем по чеклисту (раздел 9);
- ✅ разработка правил сегментации и брифов; анализ обезличенных срезов базы;
- ✅ классификация входящих ответов и черновики ответов;
- ✅ анализ статистики кампаний, отчёты, рекомендации по улучшению;
- ✅ ведение этого репозитория: шаблоны, документация, чеклисты, скрипты;
- ✅ скрипты синхронизации/очистки данных (запускаются в защищённой среде, не в GitHub);
- ✅ через подключённые MCP-коннекторы (HubSpot, Gmail и т.п.) — чтение данных, подготовка черновиков, обновление статусов **с подтверждением человека**.

Ограничения (осознанные, а не технические):

- ❌ Claude не хранит базу — только обрабатывает срезы по запросу;
- ❌ не отправляет массовые письма сам — отправка через сервис рассылок;
- ❌ не принимает необратимых решений (удаление контактов, отправка кампании) без человека — на первых этапах;
- ❌ персональные данные не попадают в промпты без необходимости и никогда — в GitHub.

## 14. Что лучше делать через сервис рассылок/CRM

| Задача | Почему сервис, а не Claude |
|--------|---------------------------|
| Физическая отправка писем | Репутация IP, троттлинг, ретраи, инфраструктура доставляемости |
| Ссылка отписки и suppression list | Автоматика, юридическая надёжность, работает даже при ошибке в сегменте |
| Трекинг open/click/bounce | Пиксели, редиректы, webhook — инфраструктурная задача |
| Обработка FBL-жалоб | Прямые контракты сервисов с почтовыми провайдерами |
| Хранение базы и согласий | Права доступа, аудит, шифрование, соответствие закону о ПД |
| Автоматические цепочки по расписанию | Надёжный планировщик с гарантией исполнения |
| A/B-тесты рассылок | Честная рандомизация и статистика «из коробки» |
| Транзакционные письма (подтверждение заказа) | Отдельный поток с высокой репутацией |

Ориентиры по выбору: **CRM** — HubSpot (уже подключён через MCP-коннектор, есть email-маркетинг внутри) или отечественные аналоги при требованиях к локализации ПД. **Сервис рассылок** — при базе в РФ разумно смотреть Unisender / Sendsay / DashaMail / NotiSend (доставляемость в Mail.ru/Яндекс, соответствие 152-ФЗ); международные альтернативы — Brevo, Mailchimp. Критерии: API + webhooks (для интеграции с Claude-агентами), suppression list, one-click unsubscribe, статистика по доменам получателей.

Разделение труда одним предложением: **Claude думает и пишет — сервис хранит и отправляет.**

## 15. Безопасный порядок внедрения

Каждый этап имеет критерий выхода; на следующий не переходим, пока критерий не выполнен.

**Этап 0. Фундамент (неделя 1–2)**
- Поддомен для рассылок, SPF/DKIM/DMARC, Google Postmaster Tools.
- Выбор сервиса рассылок и CRM-структуры (разделы 3–5), настройка полей.
- Политика данных: где живёт база, кто имеет доступ, что запрещено коммитить в GitHub.
- ✅ *Выход:* тестовое письмо с нового домена проходит проверки аутентификации (SPF/DKIM/DMARC pass) и доходит во «Входящие».

**Этап 1. База (неделя 2–3)**
- Импорт базы в CRM, верификация email, простановка `consent_status`.
- Контакты без подтверждаемого согласия — в отдельный сегмент, **не рассылать**.
- Первичная сегментация (раздел 6), suppression list.
- ✅ *Выход:* у 100% контактов заполнены `consent_status`, `email_validity`, сегмент.

**Этап 2. Пилот (неделя 3–5)**
- Welcome-цепочка на самом тёплом сегменте, партии по 20–50 писем в день (прогрев).
- Полный ручной контроль: Claude пишет → QA-чеклист → человек утверждает и отправляет.
- Reply Agent в режиме «только черновики».
- ✅ *Выход:* 2–3 кампании с open rate > 20%, жалобы < 0,1%, bounce < 2%.

**Этап 3. Масштабирование (неделя 5–8)**
- Кампании 2–3 из раздела 7, рост объёмов по графику прогрева.
- Автосинхронизация отписок сервис ↔ CRM; аналитика по каждой кампании.
- ✅ *Выход:* стабильные метрики на объёме всей активной базы, отчёты Analytics Agent выходят регулярно.

**Этап 4. Автоматизация (неделя 8+)**
- Автоматические цепочки (welcome, реактивация) на стороне сервиса.
- Claude-агентам делегируются рутинные шаги (классификация ответов, обновление статусов), человек — на утверждении контента и разборе исключений.
- Регулярный ритм: контентный план рассылок на месяц, ежемесячная гигиена базы, квартальный аудит доставляемости.
- ✅ *Выход:* система работает в ритме без ручной сборки каждой кампании; человек тратит время на стратегию и ответы горячим лидам.

**Правило отката:** при жалобах > 0,2%, bounce > 3% или падении open rate вдвое — стоп всех кампаний, разбор Analytics Agent, возврат на предыдущий этап.
